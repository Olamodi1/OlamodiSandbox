HTTP/2 and HTTP/3

The modern versions keep the same meaning for requests and responses but change how data travels.

HTTP/2 (2015)

Standardized in 2015 (RFC 7540) and based on Google's SPDY protocol from 2009. It uses the same methods, status codes and headers as before.

  • Binary framing: HTTP/1.1 was plain text; HTTP/2 is binary, which is faster and less error-prone to parse.
  • Multiplexing: many requests and responses share one TCP connection at the same time, so the 6 to 8 parallel connections are no longer needed.
  • Header compression (HPACK): headers repeat heavily, so compressing them saves bandwidth, especially for mobile apps.
  • Stream prioritization: the client signals which resources matter most, such as CSS before analytics scripts.
  • Server push: the server could send files before the browser asked for them. In practice it was hard to use well, and browsers have since scaled it back.
Remaining problem: HTTP/2 still runs on TCP. If one packet is lost, TCP pauses all streams on the connection until it is recovered.

HTTP/3 (2022)

Standardized in June 2022 as RFC 9114. The big change is that it runs on QUIC, a transport built on UDP, instead of TCP.

  • No transport-level blocking: each stream is independent, so a lost packet only delays its own stream.
  • Built-in encryption: QUIC includes TLS 1.3, so HTTP/3 is always encrypted.
  • Faster connections: a returning client can send data with zero extra round trips (0-RTT).
  • Connection migration: a connection ID, not an IP address and port, identifies the connection, so switching from Wi-Fi to cellular does not break it.

Adoption (2024 figures)

  • About 65% of websites supported HTTP/2 (W3Techs, 2024).
  • About 30% of global web traffic used HTTP/3 (Cloudflare, 2024).
  • Chrome, Firefox, Safari and Edge all support HTTP/3, and CDNs such as Cloudflare, Fastly and CloudFront have led adoption.

These numbers come from 2024 sources and will be refreshed with current data in a later milestone.
