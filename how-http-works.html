How HTTP Works

HTTP is an application-layer protocol: a set of rules for how clients and servers talk. It is stateless, so each request is independent unless cookies, sessions or tokens carry state.

The Request-Response Cycle

This is what happens when you click a link:

  1. DNS lookup: the browser translates a name like www.example.com into an IP address.
  2. TCP connection: the browser connects to port 80 (HTTP) or 443 (HTTPS) with a three-way handshake. HTTP/3 uses QUIC instead.
  3. TLS handshake (HTTPS): both sides agree on encryption keys.
  4. HTTP request: the browser asks for a resource.
  5. Server processing: the server finds the file or runs application code.
  6. HTTP response: the server returns a status code and the content.
  7. Rendering: the browser reads the HTML and requests the CSS, JavaScript and images it finds, repeating the cycle.

HTTPS and Security

HTTPS is HTTP sent over TLS (Transport Layer Security). It is not a separate protocol, just HTTP with an encryption layer that provides:

  • Confidentiality: data cannot be read in transit.
  • Integrity: data cannot be changed in transit.
  • Authentication: you are talking to the real server, proven by a certificate from a trusted Certificate Authority.

Without HTTPS, anyone on shared Wi-Fi can read passwords and session tokens sent over plain HTTP. Free certificates from Let's Encrypt (launched 2015) and browser warnings (Chrome began marking HTTP as "Not Secure" in 2018) pushed HTTPS from roughly 30% of browsing in 2013 to about 95% by 2024, according to Google's Transparency Report.

Future Directions

  • End-to-end HTTP/3: many sites use HTTP/3 only up to a CDN edge, then HTTP/2 to the origin.
  • WebTransport: a browser API on QUIC for low-latency, multiplexed streams.
  • Post-quantum cryptography: new TLS algorithms to resist quantum computers.
  • Beyond browsers: HTTP also carries gRPC, IoT traffic and real-time data.
